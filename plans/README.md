## Folder organization (binding)

Plans are filed by **deliverable**, and the status table below is the single
index whatever folder a file lives in:

| Folder | Holds | Move there when |
| ------ | ----- | --------------- |
| `plans/` (root) | Active implementation handoffs — the deliverable is product source, tests, docs or tooling changes. A characterization gate that still authorizes its fix (075, 080) stays here. | A spike's gate is approved and the build authorized; a rejected proposal is deliberately re-opened. |
| [`completed/`](completed/) | Finished work, including honest no-action closures (DONE / CLOSED-NO-ACTION). The file keeps its full completion record. | Status becomes DONE or CLOSED-NO-ACTION. |
| [`spikes/`](spikes/) | Exploration, investigation, measurement and decision/design/consumer-gated direction plans — the deliverable is evidence, a verdict or a gate answer, not a code change. | A plan is written as a gate or an investigation, or its implementation scope is withdrawn (048). |
| [`rejected/`](rejected/) | Proposals that will not be built: abandoned approaches, or findings fixed independently. The file is kept as the standing answer with the rationale. | Status becomes REJECTED. |

Moving the file is part of changing the status; the status update is not done
until the file has moved:

1. **DONE / CLOSED-NO-ACTION** → `completed/`, replace the status cell with
   `DONE (YYYY-MM-DD) — [completion record](completed/README.md#plan-NNN)` and
   add the matching `### Plan NNN` record to
   [`completed/README.md`](completed/README.md).
2. **REJECTED** → `rejected/`, keep a dated one-line rationale in both the
   status cell and the file, and leave the plan body intact as the record of
   why the approach was rejected.
3. **TODO investigation / decision gate** → `spikes/`; when the gate is
   approved and the build authorized, move it back to the root as an
   implementation plan.
4. **Update every reference to the old path**: the plan-number cell in the
   table below, the [Spikes](#spikes-6) section, the finding map, cross-plan
   links, and any note in `completed/README.md`.

Never stage, commit or push anything under `plans/` — see the policy below.

## Project execution policy (binding for every plan)

These rules override any generic improve-skill defaults (worktrees, committing
plan files). They live here so `SKILL.md` upgrades cannot drop them.

1. **Develop in the current worktree on a branch.** Create a feature branch
   from the default branch in this repo (e.g. `advisor/005-docs-landing`).
   **Do not** create a separate git worktree, `git worktree add`, or an
   isolated clone for plan execution unless the human operator explicitly
   asks for one.
2. **`plans/` is local-only.** Never `git add`, stage, commit, or push anything
   under `plans/` (including this README and status-row updates). Plans and
   status edits stay on disk for the operator; they are not part of the PR.
3. **Source changes only in commits.** When a plan says “commit”, commit only
   the in-scope product/docs files for that plan. If `git status` shows
   `plans/`, leave those paths unstaged.
4. **Status updates are still required.** Update your row in this file when
   done or blocked — just do not commit it.
5. **No push / no PR** unless the operator explicitly instructs it.
6. **Plan numbers never appear in user-facing docs or commit messages.**
   Plan numbers (001, 020, …) are local development bookkeeping only. When
   writing `docs/**`, `README.md`, `CHANGELOG.md`, or any commit message,
   describe the change itself — never reference a plan number. Check for
   stray `plan NNN` / bare `NNN` references before committing docs.
7. **Every plan that changes user-visible behaviour includes a docs step.**
   The plan body names the `docs/*.md` page(s) to update and carries the
   detailed behaviour description there; the `CHANGELOG.md` entry stays a
   concise one-or-two-sentence user-facing summary (AGENTS.md changelog
   guideline). A plan without a docs step — or with “no docs needed” — must
   justify why in its Scope section. Applies to already-written TODO plans:
   when executing one, add its docs step if the plan lacks it.

If a plan’s Git workflow section conflicts with this policy, **this section
wins.**

From the 2026-10-31 fraction-vs-date decision (issue #87 backport attempt on
`release/v0.22.0`) — recorded so it is not re-audited:

- **Standalone fraction text (`2/3`) read as a date** (the issue #87 request;
  attempted as `3cd0afd`, reverted same branch as `359916b`): a bare `n/d` at
  end-of-line is genuinely ambiguous — progress ("2 of 3 done") to one user,
  a calendar date to another — and chrono resolves it month-first (American
  M/D), so converting it silently corrupts or silently _deletes_ user text
  (the matched expression is removed when conversion fires). The attempt
  shipped the fork's ≤10-denominator heuristic; the operator rejected it on
  review as UX-fragmented — an invisible threshold splits `2/3` from `5/12`
  inside one continuous surface, and the highlighted/no-highlight feedback
  differs with no user-visible cause. Note also that `docs/editor.md`'s
  documented "Specific dates" all carry a year or a month name, so bare
  `n/d` was never in the documented grammar. **Decision (2026-10-31,
  operator): revert, and treat this as design-needed rather than a bug fix**
  — no fraction guard ships until the ambiguous bare-`n/d` space has a
  deliberate design; the issue #87 PR invitation is effectively paused until
  that design exists. Candidate to weigh when designing: bare `n/d` never
  converts (a date requires a year, a month name, or another unambiguous
  form such as `27th`), which aligns the parser with the documented grammar
  and eliminates both the wrong-month and text-deletion classes.
